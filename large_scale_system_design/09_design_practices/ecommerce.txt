Answer
For merchants
Physical products with limited inventory
title, description, categories, images, optional attributes

- Product management system for merchants to sign up create, update products and view data
- Analytics: view visitors, projected product Performance

For  users
- store front to broswe and search based on title, category, description
no registeration or review necessary
- Checkout page to view tax and bill breakdown, click to purchase and receive email  about order
shopping cart is client side, payment is third party
email and notifications at stages of purchase

Non functional
Merchant
Scalability not an issue for merchants, low traffic, thousands of products
performance but can tolerate more latency < 1s 50th percentile
consistency over availability
99.5% uptime on availability
User
Scalability very high for users 10-100 million daily users, multiple countries, sudden traffic spike
Performance < 200 ms at 50th percentile < 500ms for 99percentile
checkout < 1s response time fo 99p
availability over consistency for store front but consistency over availability for checkout
High availability no SLA for users but aim is 99.99% availability

Architectural diagram
Merchants
product management service service provides ui for merchants to register and login with a sql database
product service for product update, edit, delete with its own db nosql
images in object store
inventory service stores inventory for product ina key value store


User
store front
api gateway
browser web service
conflicting requirements for product for user and merchants, users read alot, merchants write a lot, merchants need consistency, users need availability
contention over read, write we use cqrs and create a search service which updates with message queue from products service with a no sql db with efficient text search
and index title, description and categories

analytics
product page visit, search, realtime data and historical data need lambda architecture
any time product is viewed product search send an event to broker, so will order and purchase services which an analytics lambda architecture will listen for
and consume

store checkout
- taxes servive that stores tax related data and calculates tax and sources data from products service
it uses user location and other data to calculate tax
- order service gets user billing and shipping info, send user confirmation after inventory confirmation to order service, billing and shipping async one after the other. We update user asynchronously about shipping or payment issue
after the fact via push notification
- use event sourcing pattern to store orders for complete order audit with message broker and notification sent on order update. We can also recover orders with order recovery watches every order and active order not sent to shipping
service within a time frame leads to it being taken care of by this
- payment service
- shipping service  on updates from third party services we send users notifications till delivery

Event sourcing used for failure recovery, auditing and organizational scalability(event store)

Users
store

performance use cdn for images and also generate smaller thumbnail when images for when image list is viewed as small
cache product search for popular products and query results

checkout
event driven architecture allows for high traffic
