How to chandle delays and out of order arrival of events

We have three distict timestamps for every events
- Event time: Time when event happened stored inside record  generated by client
- Ingestion/Arrival time: The moment the backend server or streaming platform (like Kafka, EventHubs, or Pub/Sub) receives and writes the event to its log.
- Processing time: event is parsed/processed by consumer service

last two are very close while first is greater than second. If application is oveloaded there may be a significant time difference

* Use arrival time when we do not care about when event happened but need to act in real time for windows e.g alerting/monitoring time like rate limiting for third party consumers where we use sliding winndow
Another is when we do not have event time or cannot trust it like a social mobile app likes and comment where time is not critical but end usertime may be incorrect/out of sync or event buffered on user device
due to loss of network or requests delayed due to low battery and batched for high efficiency

* Use event time when we care about time event occues for accurate correlation/ordering like stock market hopping window with a minute time interval showing moving average requires event ordering by time
Analysing sequence of events for tracking and analytics like language learning and optimize user experience we use event time to order as events may be sent much later or in batch as all events may arrive at the same timegiving no insight


Handling late arrival  Discard. Grace period, Watermark
Say tumbling  window is used and an event with time 0:50 arrives at the second window while time for current window starts at 1:00 and should be in the processed first window with already published event,
we might
-  discard it and lose many events or
- add a grace period to each window like 15 seconds before aggregation and any late events within this period is added to the previous window but any later events are discarded
Pros of grace period   advantages we give late events another chance
Cons We might not find right period easily too long we intorduce extra unnecessary delay but too short we lose many more events that arrive late
- We choose a watermark and once window  is closed we keep track of maximum event time we see so far and for every new event we update maximum time if needed then check if maximum event time seen so far - watermark value is less than upper bound of old window
As long as this time is less than window upper bound say 59 - 10 < 1 min we keep old window open and new event added to it so if an event with time 0:50 arrives after it is added to old window
We keep old window open and add events with time greater than the old windoow upper bound to new window. As soon as encounter an event whose evemt time minus watermack value is greater than upper bound of old window we close and aggregate the old window
Pros: watermark is not tied to arrival of event
Cons: Delay aggregations/close window without ability to estimate it
